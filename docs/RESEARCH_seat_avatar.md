## 0. 요약 (먼저 읽을 것)

1. **단면도(옆에서 본 그림)를 쓰기로 한 결정이 리서치를 크게 단순화한다.** 단면도에서 의미 있는 축은 `층`과 `무대로부터의 거리(열)`, 그리고 `무대 뒤(합창석)인가` 세 가지뿐이다. A블록이 왼쪽인지 오른쪽인지는 **그릴 필요가 없다**. 그래서 가장 불확실한(그리고 공식 출처를 찾기 어려운) 좌우 배치 정보를 아예 안 써도 된다.
2. **파서는 이미 있다.** 새로 짜지 말고 `parseSeat()`를 보강해야 한다. 실제 티켓 사진에서 확인된 심각한 오탐 벡터가 최소 3개 있다 (§2.3).
3. **아바타는 DiceBear `pixel-art` 스타일이 사실상 정답이다.** 아트가 **CC0 1.0**(귀속 불필요, 상업 이용 가능), 코드가 MIT, 캔버스가 정확히 **16×16 픽셀**이고 SVG에 `shape-rendering="crispEdges"`가 박혀 나온다. npm 로컬 번들로 완전 오프라인 동작. 직접 그릴 이유가 없다. `[확인]`
4. **렌더링은 인라인 SVG.** Canvas/box-shadow/스프라이트시트보다 이 용도에 명확히 유리하다 (§3.1).

## 1. 한국 공연장 좌석 표기 체계

### 1.1 실물 티켓에서 직접 확인한 표기 (최우선 근거)

`testdata/_raw_screenshots/` 의 티켓 사진 4장을 직접 판독한 결과. **이게 이 문서에서 가장 신뢰도 높은 자료다.** `[확인]`

**롯데콘서트홀 (LOTTE CONCERT HALL)**

| 항목 | 인쇄 문자열 |
|---|---|
| 입장 | `8층 2번 게이트` |
| 입장 | `입장게이트: 9F 8번 GATE` |
| 좌석 | `좌석: 객석 1층 B구역 15열 01번` |
| 좌석 | `객석1층 R구역 01열 12번` |
| 좌석 | `객석1층 C구역 08열 01번` |
| 등급+금액 | `R석` / `470,000원` (별도 줄) |
| 등급+금액 | `S석 21,000원` |
| 초대권 | `<초대교환권>` … `R석 초대` … `롯데콘서트홀 표준좌석` (좌석번호 없음) |

핵심 관찰:
- **롯데는 "구역"** 을 쓴다. 접두어 `객석`이 붙는다 (`객석 1층`, `객석1층` — 공백 유무 둘 다 존재).
- 열/번이 **zero-pad** 된다: `01열`, `08열`, `01번`.
- ⚠️ **`8층 2번 게이트` / `9F 8번 GATE` 가 같은 티켓 위에 있다.** 여기서 "8층/9F"는 **건물 층(게이트 위치)** 이지 객석 층이 아니다. 그리고 "2번"은 게이트 번호다. 좌석 파서가 이 문자열을 같이 먹으면 `floor=8, number=2`로 완전히 틀린다. (§2.3-A)

**예술의전당 (SAC)**

| 항목 | 인쇄 형태 |
|---|---|
| 좌석 (표 형태) | `1층`(Floor) · `A블록`(Block) · `15열`(Row) · `10번`(Seat) |
| 좌석 | `3층` · `E블록` · `6열` (번 칸 없음/비어 있음) |
| 좌석 | `3층` · `B블록` · `4열` · `6번` |
| 등급 | `회원석` (일반 R/S/A석이 아님) |
| 공연장 | `콘서트홀` 이 별도 필드로 크게 인쇄 |

핵심 관찰:
- **예당은 "블록"** 을 쓴다. 롯데의 "구역"과 다르다.
- 값이 **표(칼럼) 레이아웃**으로 흩어져 있고 각 칸 아래에 영문 소캡션 `Floor / Block / Row / Seat` 이 붙는다. → OCR이 한 줄로 이어 붙일 때 `1층 A블록 15열 10번` 이 되지만, **칼럼 순서가 뒤바뀌거나 영문 캡션이 섞여 들어올 수 있다** (`1층 Floor A블록 Block 15열 Row`).
- **번(Seat)이 아예 없는 티켓이 실재한다** (회원음악회 티켓). 자유석/블록지정석.
- 등급이 `회원석`처럼 **한글 등급**일 수 있다. 현재 파서의 `[A-Z]{1,2}석` 정규식은 이걸 못 잡는다.

블록 구성 (공식 배치도 원문은 PDF 다운로드로만 제공되어 미확보):

- 1층: `A B C D E` 블록. C가 중앙, A/E가 양 끝. `[교차]` (블로그 2곳 + 칼럼)

- 2층: `BOX 1~3` (한쪽) + `A~E 블록` + `BOX 4~6` (반대쪽) `[단일]`
- 3층: `BOX 7~9` + `A~G 블록` + `BOX 10~12` `[단일]`
- 등급: R석 / S석 / A석 (공연마다 2~5개 등급까지 분류 가능) `[확인]` 공식 대관안내

> ⚠️ 2층·3층의 블록 구성과 BOX 번호는 **블로그 1곳**이 출처다. 그대로 코드에 넣지 말 것. 단면도에는 어차피 "2층", "3층" 밴드만 필요하므로 **쓸 일이 없다**. 필요해지면 공식 좌석배치도 PDF를 받아 확인할 것.
> ⚠️ "A블록이 왼쪽"이라는 서술은 **누구 기준의 왼쪽인지(객석에서 본 왼쪽 vs 무대에서 본 왼쪽) 명시되어 있지 않다.** `[미확인]`

구역 코드 (공식 객석안내 페이지에 표기된 목록): `LP, L, A, B, C, D, E, R, RP, P` `[확인]`

- `LP` / `RP` = **합창석 영역(무대 뒤)** `[단일]` (나무위키 계열 서술)
- `P` = 파이프오르간 앞쪽(무대 뒤) `[단일]`
- `L` / `R` = 측면(발코니/테라스) 구역 `[교차]` — 실물 티켓 `객석1층 R구역 01열 12번`이 "열 수가 적은 측면 구역"과 정합
- 2층에도 `A~E` 및 `L, R` 구역이 있음 `[단일]` (artinsight 칼럼)
- ⚠️ **상충하는 서술 있음**: artinsight 칼럼은 1층을 "A구역(1~8열) / B구역(9~16열) / C구역(17~23열)"이라는 **깊이 밴드**로 설명하는데, 공식 페이지의 구역 목록(LP·L·A~E·R·RP·P)과 다른 체계다. 어느 쪽이 현행인지 **미확인**. 단면도에는 "열 번호로 깊이를 정한다"는 규칙만 쓰면 되므로 이 충돌을 피해갈 수 있다.
- ⚠️ 빈야드 구조라 **공연마다 R/S/A 등급 배분이 달라진다** `[단일]`. 즉 **등급 → 좌석 위치 매핑은 신뢰할 수 없다.**

## 2. 좌석 문자열 파서 설계

### 2.1 현재 상태

목표 스키마 `ParsedSeat`는 **이미 `app/services/ocrSchema.ts:15`에 정의되어 있고**, `parseSeat()`도 구현되어 있다. 새로 만들 필요 없음. 아래는 **차이(gap) 분석 + 보강안**이다.

현재 구현 요약:
- 층: `/(\d{1,2})\s*층/` → 1~20 범위 검증
- 구역: `/([A-Za-z]{1,3}|[가-힣]{1,2})\s*(?:구역|블록|블럭|존)/` + `NOT_A_BLOCK` 블랙리스트
- 열: `/(\d{1,3})\s*열/` → 1~200
- 번: `/(\d{1,3})\s*번(?!호)/` → 1~500
- 등급: `/(VVIP|VIP|[A-Z]{1,2})\s*석/i`
- confidence: 채워진 필드 수 기반 `0.4 + 0.15 * parts`

이미 잘 된 부분: raw 보존, 실패 시 confidence 0, 범위 검증, `NOT_A_BLOCK` 블랙리스트, `번(?!호)` 로 "예매번호" 방어.

### 2.2 스키마 확장 제안

단면도를 그리려면 현재 필드로는 부족하다. 3개 추가를 권장한다. `[추론]`

```
interface ParsedSeat {
  floor: number | null;
  block: string | null;
  row: number | null;
  number: number | null;
  grade: string | null;
  raw: string;
  confidence: number;

  // --- 추가 제안 ---
  rowLabel: string | null;   // 'A' 같은 알파벳 열 (V12). 숫자면 null
  behindStage: boolean;      // 합창석/무대 뒤 여부 (V14). 단면도 배치에 필수
  seatNumbers: number[];     // 연석 (V11). number는 seatNumbers[0]과 동일하게 유지
}
```

`behindStage`가 왜 필요한가: 단면도에서 무대 뒤 좌석은 **무대 반대편**에 그려야 한다. 이걸 `block` 문자열에서 매번 다시 판정하면 공연장별 규칙이 렌더러로 새어 나간다. 파싱 시점에 venue 프로필을 참조해 한 번만 정하는 게 맞다. `[추론]`

> **`floor` 범위를 좁혀야 한다.** 현재 1~20인데, 국내 클래식 공연장 객석은 최대 3~4층이다(예당 콘서트홀 3층, 세종대극장 3층, 롯데 2층). `1~5`로 조이면 §2.3-A의 게이트 층 오탐(8층/9F)이 **범위 검증만으로 자동 차단**된다. 가장 비용이 낮은 개선이다. `[추론]`

### 2.3 반드시 고쳐야 할 오탐 3가지

**A. 게이트 문자열 오염 (V5) — 심각도 최상**

실물 롯데 티켓에 `입장: 8층 2번 게이트` 와 `좌석: 객석 1층 B구역 15열 01번` 이 **나란히** 인쇄된다. LLM이 seatRaw를 만들 때 두 줄을 붙이면 현재 파서는 `floor=8`(첫 매치), `number=2`(첫 매치)로 읽는다.

3중 방어 권장:
1. **전처리 제거**: `/[^\s]*\d+\s*번?\s*(게이트|GATE|gate)/` 및 `/입장\s*(게이트)?\s*:?[^\n]*/` 를 파싱 전에 잘라낸다.
2. **`객석` 앵커 우선**: `/객석\s*(\d{1,2})\s*층/` 이 매치되면 **그 값을 무조건 채택**하고 다른 층 매치를 무시한다. 롯데는 항상 `객석`을 붙인다 `[확인]`.
3. **범위 축소**: `floor ∈ 1..5`.
4. (프롬프트 측) `ocrSchema.ts`의 OCR 지침에 "게이트/입장 정보는 seatRaw에 넣지 마세요"를 **명시적 negative 예시로** 추가. 현재 지침에는 예매번호 경고만 있다.

**B. 한글/장문 등급 미탐 (V9, V10)**

`/(VVIP|VIP|[A-Z]{1,2})\s*석/i` 는 실물에서 확인된 `회원석`을 못 잡고, `BOX석`(3글자)도 못 잡는다. 또 `/i` 플래그 때문에 소문자 영단어 뒤에 `석`이 오면 오탐 가능.

권장: **화이트리스트 우선 + 영문 등급 폴백** 순서로.
- 화이트리스트: `VVIP석 VIP석 R석 S석 A석 B석 C석 D석 회원석 학생석 초대석 합창석 시야제한석 제한석 보류석 자유석 BOX석 박스석`
- 폴백: `/\b(VVIP|VIP|[A-Z])석/`  (대문자 강제, 1글자로 제한 → `객석`·`합창석` 등 오탐 감소)

**C. 등급과 구역의 충돌 (롯데 R구역 vs R석)**

`객석1층 R구역 01열 12번` — 여기서 `R`은 **구역**이다. 그런데 `R석`이라는 **등급**도 존재한다. 현재 파서는 `구역` 접미사를 요구하므로 우연히 잘 동작한다. **이 동작을 회귀 테스트로 고정할 것.** 등급 정규식을 느슨하게 바꿀 때 깨지기 쉽다. `[추론]`

### 2.4 추가 보강 (우선순위 중)

- **V4 영문 캡션**: 파싱 전 `/(Floor|Block|Row|Seat|Gate|Grade)/gi` 를 공백으로 치환. 예당 표 레이아웃 대응.
- **V16 영문 층**: `/(\d{1,2})\s*F\b/` 추가. 단 게이트 제거 **이후**에 적용해야 `9F`를 안 먹는다.
- **V15 OCR 오인**: 블록 후보가 1글자일 때만 `0→O, 8→B, 5→S, 6→G, 1→I` 정규화 적용. 열/번 숫자에는 **절대 적용하지 말 것** (숫자를 글자로 바꾸면 더 나쁨).
- **V11 연석**: `/(\d{1,3})\s*[,~\-]\s*(\d{1,3})\s*번/` 를 먼저 시도해 `seatNumbers` 채우기.
- **V12 알파벳 열**: `/([A-Z])\s*열/` → `rowLabel`. 단 `block`이 아직 비어 있고 `구역|블록` 키워드가 문자열에 전혀 없을 때만 (세종식 `B열`=구역 혼용 대응).
- **V14 behindStage**: venue 프로필 조회. 없으면 `/합창석|CHORUS/i` 만으로 판정.

### 2.5 confidence 재설계

현재 `0.4 + 0.15 * parts` 는 "층만 있음"과 "번만 있음"을 동일하게 취급한다. 단면도 배치에서 **층의 가치가 압도적으로 크므로** 가중치를 다르게 줄 것을 권장. `[추론]`

```
w = { floor: 0.35, row: 0.25, block: 0.20, number: 0.10 }
base   = Σ w[채워진 필드]
bonus  = +0.10  (venue 프로필과 block 코드가 일치할 때)
grade만 있을 때 = 0.30   // 단면도를 그릴 수는 없음
```

`ocrSchema.ts:567`가 `seatRaw.confidence * seat.confidence` 로 곱하고 있는데, 이 구조는 유지하는 게 맞다 (OCR 신뢰도와 파싱 신뢰도는 독립).

### 2.6 실패/부분 성공 처리 정책

렌더링 관점에서 4단계로 나눌 것을 권장. `[추론]`

| 등급 | 조건 | 화면 처리 |
|---|---|---|
| **EXACT** | `floor` + `row` 존재 | 단면도의 정확한 좌표에 아바타 배치 |
| **APPROX** | `floor`만 존재 | 해당 층 밴드 **중앙**에 배치 + "대략적인 위치예요" 캡션 |
| **GRADE_ONLY** | `grade`만 존재 (초대권 등) | 단면도는 그리되 아바타는 **무대 앞 로비/객석 밖**에 두거나, 등급→층 추정 배치 + 점선 테두리로 "추정" 표시 |
| **NONE** | 전부 실패 | 단면도 없이 티켓 스텁만. **"좌석 정보를 입력할래요?" 수동 입력 CTA** |

원칙 3개:
1. **raw는 절대 버리지 않는다** (이미 그렇게 되어 있음). 파서를 개선하면 저장된 raw를 재파싱해 소급 적용할 수 있다.
2. **부분 성공을 실패로 취급하지 않는다.** 층만 알아도 그림은 그려진다 — 이게 단면도 방식의 최대 장점이다.
3. **추정한 것은 시각적으로 티가 나야 한다.** 실선 = 확정, 점선/반투명 = 추정. 사용자가 틀린 걸 보고 고칠 수 있게.
4. **등급→층 추정은 하지 말거나, 하더라도 매우 약하게.** 롯데는 빈야드 구조라 공연마다 등급 배분이 바뀐다 `[단일]`. R석이 1층이라는 보장이 없다.

### 2.7 수동 보정 UI를 반드시 넣을 것 `[추론]`

OCR + 정규식 조합은 위 변형 16종을 100% 못 잡는다. **층/구역/열/번 4개짜리 드롭다운 + 숫자 입력**을 아바타 옆에 두는 게, 파서를 20% 더 정교하게 만드는 것보다 비용 대비 효과가 크다. 사용자가 고친 값은 `ParsedSeat`에 `source: 'ocr' | 'manual'`로 표시해 저장.

## 3. 픽셀아트 단면도 구현 방법

### 3.1 렌더링 방식 비교 → **인라인 SVG 채택**

| 방식 | 장점 | 단점 | 이 용도 적합성 |
|---|---|---|---|
| **인라인 SVG** | 벡터라 배율 무관 선명 / DOM이라 좌석 클릭·툴팁·CSS 테마 가능 / **DiceBear가 이미 SVG를 뱉음(변환 0단계)** / React 렌더링과 자연스럽게 통합 / 다크모드 CSS 변수 적용 가능 | 요소 수천 개 넘으면 느려짐 | ✅ **최선** |
| Canvas 2D | 요소 많을 때 빠름 | DiceBear SVG를 Image로 래스터화하는 비동기 단계 필요 / 히트테스트 직접 구현 / DPR·정수배율 관리 수동 / React와 궁합 나쁨 | ❌ 과잉 |
| CSS grid + box-shadow | 빌드 없이 순수 CSS | **성능 재앙**. 800개 그림자 부근부터 눈에 띄게 느려짐 / 좌표 계산 지옥 | ❌ |
| 스프라이트 시트(PNG) | 화풍 자유도 최대 | 에셋 파이프라인 필요 / `image-rendering: pixelated` 필수 + 브라우저별 힌트 신뢰 불가 / 아바타 조합 수 폭발 시 시트 관리 불가 | ❌ |

**결정 근거 (핵심)**: 이 화면의 요소 수는 수백 개 수준(배경 패널 + 층 밴드 + 무대 + 아바타 1개)이라 SVG의 성능 한계에 근처도 못 간다. 반면 SVG만 주는 이점(DiceBear 무변환 삽입, 클릭 가능한 좌석, 무한 선명)은 전부 필요하다. `[추론]` — 성능 특성 자체는 `[교차]`

### 3.2 픽셀아트 선명도: 필수 속성

**벡터로 그릴 때(권장):**
```
shape-rendering="crispEdges"   /* SVG 속성. 안티에일리어싱 끔 */
```
- DiceBear `pixel-art` 스타일 정의 JSON의 `attributes` 에 **정확히 `{"fill":"none","shape-rendering":"crispEdges"}`** 가 들어 있다. `[확인]` (`@dicebear/styles@10.5.0/dist/pixel-art.min.json` 직접 확인)
- 단면도 배경도 같은 속성을 쓰면 아바타와 화풍이 자동으로 일치한다.

**래스터(PNG)를 섞을 때:**
```css
image-rendering: pixelated;              /* 표준 */
image-rendering: crisp-edges;            /* 일부 브라우저 */
image-rendering: -webkit-optimize-contrast;
```
Canvas면 추가로 `ctx.imageSmoothingEnabled = false`.

**⚠️ MDN이 명시한 함정 2개** `[확인]`:
1. `image-rendering` 은 **힌트일 뿐** 브라우저별로 일관되지 않는다.
2. `devicePixelRatio` 가 정수가 아니거나 브라우저 줌이 110% 같은 값이면 **픽셀 폭이 들쭉날쭉해진다**. → 확대는 반드시 **정수 배율**로.

### 3.3 좌표계 설계

**논리 캔버스를 고정한다.** 제안: `160 × 96` 아트픽셀 (5:3). 아바타가 16×16이므로 화면 가로의 1/10 — 한 명이 잘 보이는 크기. `[추론]`

```
ART_W = 160, ART_H = 96      // SVG viewBox="0 0 160 96"
AVATAR = 16                   // DiceBear pixel-art 캔버스 = 16×16  [확인]
```

**venue 프로필 데이터 구조 제안** `[추론]`:

```
VenueProfile {
  id: 'sac-concert-hall'
  names: ['예술의전당 콘서트홀', '예술의전당', 'SAC', '콘서트홀']   // 매칭용 별칭
  blockWord: '블록' | '구역'
  stage: { x, y, w, h }                       // 아트픽셀 좌표
  floors: [
    { floor: 1, y: 68, h: 12, x0: 44, x1: 152, maxRow: 24 },
    { floor: 2, y: 50, h: 10, x0: 60, x1: 152, maxRow: 10 },
    { floor: 3, y: 32, h: 10, x0: 60, x1: 152, maxRow: 10 },
  ]
  behindStageBlocks: ['F','G','H']            // 예당. 롯데는 ['LP','RP','P']
  behindStageBand: { y: 40, h: 12, x0: 8, x1: 34 }
  fallback: false
}
```

`floors[].maxRow` 는 **정확할 필요가 없다**. 열 번호를 0~1로 정규화하는 데만 쓰고, 실제 값이 초과하면 clamp 하면 된다. "층/구역 정도만 대략 맞추면 된다"는 요구사항과 정확히 일치한다.

**매핑 함수 (의사코드)**:

```
seatToXY(seat, profile):
  band = seat.behindStage ? profile.behindStageBand
                          : profile.floors.find(f => f.floor === seat.floor)
  if (!band) band = profile.floors[0]                       // 층 불명 → 1층 가정 + APPROX 표시

  t = seat.row != null ? clamp(seat.row / band.maxRow, 0, 1)
                       : 0.5                                 // 열 불명 → 밴드 중앙
  x = round(lerp(band.x0, band.x1, t))

  // 블록은 단면도에서 좌우를 표현할 수 없다.
  // 대신 "레인"으로 미세한 세로 오프셋을 줘서 같은 층/열에서도 그림이 겹치지 않게 한다.
  lane = seat.block ? hash(seat.block) % 2 : 0               // 0 or 1
  y = band.y + lane

  return { x: x - AVATAR/2, y: y - AVATAR }                  // 아바타 발끝이 좌석 바닥에 오도록
```

핵심: **정수 좌표만 쓴다** (`round`). 아트픽셀 격자를 벗어나면 픽셀아트가 깨진다.

**venue 매칭**: OCR의 `venue` 문자열은 지저분하다(`콘서트홀`만 인쇄된 예당 티켓 `[확인]`). `names` 별칭 배열로 부분 문자열 매칭하고, 실패하면 `fallback: true`인 **범용 3층 홀 프로필**로 떨어뜨린다. 프로필이 없다고 화면이 비면 안 된다.

### 3.4 반응형 / 확대·축소

**정수 배율만 사용한다.** `[추론]` (근거: MDN의 DPR 경고 `[확인]`)

```
scale = max(1, floor(containerWidth / ART_W))
svg width  = ART_W * scale
svg height = ART_H * scale
```
- `ART_W=160` 기준: iPhone(가로 ~390px) → scale 2 (320px). 태블릿 → 4~6. 데스크톱 → 6~8.
- 컨테이너 폭에 딱 맞추고 싶으면 SVG를 `width:100%`로 늘리지 말고, **컨테이너를 `justify-content:center`로 두고 SVG는 정수 크기 유지**. 좌우 여백이 생기는 게 픽셀이 뭉개지는 것보다 낫다.
- 확대 UI는 **1x / 2x / 4x 버튼**(정수 스텝)을 권장. 연속 핀치줌은 픽셀 격자를 깬다.
- 팬/줌 라이브러리가 정말 필요하면 **`react-zoom-pan-pinch` (MIT, 주간 다운로드 ~170만)** `[교차]`. 다만 이 화면은 단일 소형 단면도라 **라이브러리 없이 정수 스텝 버튼으로 충분**하다는 게 내 판단. `[추론]`

세로가 아주 좁을 때(가로 모드 등)는 `scale = max(1, min(floor(w/ART_W), floor(h/ART_H)))` 로 양축 clamp.

### 4.3 API — 버전 주의 `[확인]`

npm dist-tags 실측: `@dicebear/core` latest = **10.6.1** (MIT), `@dicebear/collection` latest = **9.4.2** (v9 계열까지만 존재).

**v9 (`@dicebear/core` + `@dicebear/collection`)** — 옵션이 **배열**
```
import { createAvatar } from '@dicebear/core';
import { pixelArt } from '@dicebear/collection';

const avatar = createAvatar(pixelArt, {
  seed: 'x',
  hair: ['long01'],          // 배열 원소 1개 = 사실상 고정
  backgroundColor: ['b6e3f4'],
});
avatar.toString();  avatar.toDataUri();  avatar.toJson();
```

**v10 (`@dicebear/core` + `@dicebear/styles`)** — 옵션이 **가중치 맵**
```
import { Style, Avatar } from '@dicebear/core';
import definition from '@dicebear/styles/pixel-art.json' with { type: 'json' };

const avatar = new Avatar(new Style(definition), {
  seed: 'x',
  topVariant: { short01: 2, long01: 1 },   // 매핑 안 된 variant는 제외, 0이면 배제
});
avatar.toString();  avatar.toDataUri();  avatar.toJSON();
```

> ⚠️ **v9 → v10에서 패키지명·API가 모두 바뀐다.** 프리셋 조합형(= variant를 고정) 용도에는 **v9의 "배열 원소 1개" 방식이 훨씬 직관적**이다. `[추론]` 다만 v10이 최신이고 다국어 포팅(byte-identical 출력) 보장이 있다 `[단일]`. **처음에 하나를 고르고 버전을 lock 할 것.**
> ⚠️ v10의 옵션 키 이름(`topVariant` 등)이 pixel-art의 파트명(`hair`, `clothes`…)과 어떻게 대응되는지는 **미확인**. 도입 시 실제로 한 번 찍어봐야 한다.

**React 삽입**: `avatar.toString()` 결과를 `dangerouslySetInnerHTML` 로 넣거나(SVG 태그 유지), 단면도 SVG 안에는 **중첩 `<svg x y width="16" height="16" viewBox="0 0 16 16">`** 로 넣는 것이 좌표 계산이 가장 단순하다. `toDataUri()` + `<image>` 도 가능하지만 벡터 이점이 줄어든다. `[추론]`

**오프라인**: HTTP API(api.dicebear.com)를 쓰지 말고 **npm 패키지만** 쓰면 네트워크 호출 0. 이 프로젝트 요구사항(외부 CDN 회피)에 맞는다. `[확인 — 라이브러리가 로컬에서 SVG를 생성]`

### 4.4 아바타 설정 직렬화

**seed 문자열만 저장하지 말 것.** `[추론]` 이유:
- seed는 "랜덤이지만 재현 가능"할 뿐, **사용자가 고른 조합**을 표현하지 못한다. 프리셋 메이커 UX와 맞지 않는다.
- DiceBear 버전이 올라가 variant가 추가/재정렬되면 같은 seed가 다른 그림을 낸다.

**권장 스키마**:
```
interface AvatarConfig {
  v: 1;                      // 이 스키마 버전
  style: 'pixel-art';
  styleVersion: '10.5.0';    // 정의 JSON 버전. 재현성 감사를 위해 기록
  parts: {
    hair: 'long01' | ...;    // 45
    eyes: string;            // 12
    mouth: string;           // 23
    clothes: string;         // 23
    beard?: string;          // 8, 없으면 미착용
    glasses?: string;        // 14
    hat?: string;            // 10
    accessories?: string;    // 4
  };
  colors: {
    skin: string;            // '#ffdbac' — 팔레트 인덱스가 아니라 hex를 저장
    hair: string;
    clothing: string;
    eyes?: string; glasses?: string; hat?: string; mouth?: string; accessories?: string;
  };
}
```

- **인덱스(`{hair: 3}`)가 아니라 문자열 키(`{hair: 'long01'}`)로 저장할 것.** DiceBear가 정의에서 variant를 추가/삭제하면 인덱스는 조용히 다른 그림을 가리키지만, 이름은 없어졌을 때 **명시적으로 실패**한다. `[추론]`
- 색상도 팔레트 인덱스가 아니라 hex 원문 저장. 팔레트가 바뀌어도 안전.
- 렌더 결과 SVG 문자열을 **캐시로 같이 저장**해두면 라이브러리 버전이 바뀌어도 과거 아카이브의 그림이 안 바뀐다. `localStorage` 또는 IndexedDB. 하나당 몇 KB.
- 저장 위치: 사용자당 아바타 1개면 `localStorage`로 충분. 티켓별로 다른 아바타(그날의 옷차림!)를 붙이는 확장을 노린다면 티켓 레코드에 `avatarConfig`를 함께 넣는 설계를 지금 해둘 것. `[추론]`

### 4.5 직접 그려야 한다면 (DiceBear를 안 쓸 경우)

필요 없다고 판단하지만, 요구사항에 있으므로 최소 레이어 목록만. `[추론]`
z-order 아래→위: `배경 → 몸/옷 → 목 → 얼굴(피부) → 귀 → 헤어(뒷머리) → 눈썹 → 눈 → 코 → 입 → 수염 → 안경 → 헤어(앞머리) → 모자 → 소품(악기/꽃다발/프로그램북)`
16×16 그리드, 파트별 SVG `<path>` 하나, 색상은 `fill="var(--skin)"` 식으로 CSS 변수화. **클래식 앱다운 차별화 소품**(바이올린 케이스, 프로그램북, 오페라글라스)만 DiceBear 위에 자체 레이어로 얹는 하이브리드가 현실적. CC0라서 이런 파생·혼합이 법적으로 자유롭다.

## 6. 구현 권고 (코드 담당이 바로 쓸 것)

### 6.1 의존성

```
npm i @dicebear/core@9 @dicebear/collection@9
```
- v9 선택 이유: variant 고정이 `hair: ['long01']` 배열 1개로 끝나 프리셋 메이커와 직결. v10의 가중치 맵은 이 용도에 우회로다.
- **버전을 정확히 lock 할 것** (`^` 쓰지 말 것). 아바타 재현성이 곧 아카이브 신뢰성이다.
- 팬/줌 라이브러리는 **처음엔 넣지 말 것**. 정수 배율 버튼으로 시작.

### 6.2 파일 배치 제안

```
app/services/ocrSchema.ts        # 기존. parseSeat() 보강만
app/services/venueProfiles.ts    # 신규. VenueProfile[] + matchVenue() + seatToXY()
app/services/avatarConfig.ts     # 신규. AvatarConfig 타입 + DiceBear 옵션 변환 + 직렬화
app/components/SeatMap.tsx       # 신규. 인라인 SVG 단면도
app/components/AvatarMaker.tsx   # 신규. 파트별 프리셋 선택 UI
```
`ocrSchema.ts`는 브라우저 API 금지 규칙이 있으므로(파일 상단 주석) `venueProfiles.ts`도 **순수 함수만** 두어 eval 파이프라인에서 같이 테스트할 수 있게 할 것.

### 6.3 작업 순서 (의존 관계상 이 순서가 맞다)

1. **`parseSeat()` 방어 강화** — 게이트 오염 제거, `floor` 범위 1~5, 한글 등급 화이트리스트. 가장 싸고 효과 큼.
   회귀 테스트 케이스 (전부 실물 확인된 문자열):
   - `객석 1층 B구역 15열 01번` → `{1, 'B', 15, 1}`
   - `객석1층 R구역 01열 12번` → `{1, 'R', 1, 12}` (R을 등급으로 오인하면 실패)
   - `객석1층 C구역 08열 01번` → `{1, 'C', 8, 1}`
   - `3층 E블록 6열` → `{3, 'E', 6, null}`
   - `1층 A블록 15열 10번` → `{1, 'A', 15, 10}`
   - `입장: 8층 2번 게이트 좌석: 객석 1층 B구역 15열 01번` → **`{1, 'B', 15, 1}`** ← 현재 코드는 여기서 깨진다
   - `9F 8번 GATE 객석1층 C구역 08열 01번` → **`{1, 'C', 8, 1}`**
   - `R석 초대` → `{null,null,null,null, grade:'R석'}`, confidence ≈ 0.3
   - `S석 21,000원` → grade만
   - `회원석` → grade `'회원석'` ← 현재 코드는 못 잡는다
2. **`ParsedSeat`에 `behindStage` 추가** + `venueProfiles.ts` 최소 3개(예당 콘서트홀 / 롯데 / 세종대극장) + `fallback` 1개.
3. **`SeatMap.tsx`** — 배경 단면도만. 아바타 없이 층 밴드에 점(`●`) 찍는 수준으로 먼저 동작 확인.
4. **DiceBear 붙이기** — 고정 seed 아바타 하나를 좌표에 배치.
5. **`AvatarMaker.tsx`** — 파트별 좌우 화살표 선택 UI. 8개 파트 중 **`hair / eyes / mouth / clothes` 4개 + `skin/hair/clothing` 색상 3개로 시작**. 모자·안경·수염·액세서리는 2차.

### 6.4 확정 상수

```
ART_W = 160;  ART_H = 96;      // 단면도 논리 캔버스 (아트픽셀)
```

### 6.5 하지 말아야 할 것

- ❌ **실제 좌석배치도 좌표를 데이터로 넣으려는 시도.** 공식 배치도는 PDF 다운로드로만 제공되고 블록별 정확한 좌표는 공개되어 있지 않다. 단면도 결정으로 이 문제를 회피한 것이므로 되돌리지 말 것.
- ❌ **등급(R석/S석)으로 층을 추정하는 것.** 롯데는 공연마다 등급 배분이 바뀐다 `[단일]`. 틀린 위치를 자신 있게 보여주면 앱 신뢰도가 깨진다.
- ❌ **블록 알파벳의 좌우 위치를 전 공연장 공통 규칙으로 가정하는 것.** 세종은 A~E가 좌→우, 롯데 칼럼은 A~C가 앞→뒤로 서술된다. **공연장마다 다르다** — 이건 확실하다.
- ❌ **DiceBear HTTP API 사용.** npm 로컬 번들만.
- ❌ **비정수 배율 확대 / 연속 핀치줌.** 픽셀 격자가 깨진다 `[확인 — MDN]`.
- ❌ **아바타를 seed 문자열로만 저장.** 라이브러리 업데이트로 과거 아바타가 바뀐다.
- ❌ **DiceBear의 다른 스타일을 라이선스 확인 없이 추가.** CC BY 4.0(귀속 필수) 스타일이 14개, 별도 약관이 4개 있다 `[확인]`.
