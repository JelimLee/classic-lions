## 2. 판독 방법 · 규칙

**이미지를 직접 보고 적었다. OCR 출력은 베끼지 않았다.**
4032×3024 원본에서 티켓 영역을 잘라 최대 4배 확대해 글자를 확인했다(`work/crops/`).

세 가지 상태를 구분한다 (`ground_truth_mine.json` 의 `read_policy`):

| 상태 | 처리 |
|---|---|
| 완전히 읽힘 | 인쇄된 그대로 기록 |
| 일부만 보임 (프레임 밖·앞 티켓·손가락) | **읽히는 부분만** 그대로 기록 + `partial_fields` 에 명시. 복원·추측하지 않는다 |
| 전혀 못 읽음 / 인쇄 안 됨 | `null` + `unreadable_fields` |

- `date` 는 zero-padded `YYYY-MM-DD`. **촬영일로 대체하지 않았다** — 촬영일은 `capturedOn` 에 따로 있다.
- 티켓이 2장이면 **가장 앞·가장 완전하게 보이는** 1장을 `truth`, 나머지는 `companion_seats_raw`.
- `gate_raw` 는 전부 기록했다. 예술의전당 티켓에는 **게이트 인쇄 자체가 없다** → `null`.
- 실명·예매번호·QR 이 보이면 `has_pii: true`.

### 3-2. 불일치 · 정정

**① `IMG_5212` 가 티켓 사진 목록에서 빠져 있었다.**
분류표는 롯데 ticket 5장인데 실제로는 6장이다. `IMG_5212` 는 티켓 2장이 프레임 안에
있지만 완전히 아웃포커스다. (§1)

**② `IMG_9623`/`IMG_9624` 는 "OCR 미실행"이 아니라 "판독 불가"다.**
이전 문서는 쿼터 소진으로 미실행이라 적고 재실행 대기로 남겼다. 원본 4032×3024 를 직접
열어 확대해 보면 **초점이 무대에 맞아 티켓이 완전히 뭉개져 있다.** macOS Vision 도 0줄을 낸다.
**어떤 모델을 다시 돌려도 이 두 장에서는 값이 나오지 않는다** — 나오면 그게 할루시네이션이다.
(정답지에서 기권(abstain) 케이스로 썼다.)

**③ `IMG_5211`/`5213` 동반석 블록 — 이전 값이 맞고 OCR 이 틀렸다.**
이전 문서: `1층 LP구역 08열 08번`. **macOS Vision 은 confidence 1.0 으로 `D구역 08열 08번`
이라고 읽는다.** 4배 확대해 글자를 직접 확인한 결과 **`LP` 가 맞다** — 앞 티켓 가장자리가
`P` 의 아랫부분(세로 획)을 잘라서 `D` 처럼 보인다. 근거 크롭: `work/crops/z5211_seatline.jpg`.
> 이 오독이 하이브리드 파이프라인에 그대로 전파돼 `IMG_5211` 의 seat 4필드를 통째로 틀렸다(§4).
> **Vision 의 confidence 1.0 은 "맞다"는 뜻이 아니다.**

**④ `IMG_7968` 동반석의 열 번호는 확인 불가다.**
이전 문서: `1층 D블록 2열 7번`. 내가 본 것은 **`7번` 뿐**이다. 열 숫자는 앞 티켓 가장자리에
아래쪽이 잘려 위 곡선만 남아 2/3/7 을 구분할 수 없고, 층·블록은 아예 가려 있다.
앞 티켓이 `2열 8번` 이니 `2열 7번` 이 자연스럽지만 **사진만으로는 단정할 수 없어** `7번` 만 적었다.

**⑤ "롯데 티켓은 전부 상단 스텁만 찍혔다"는 설명이 `IMG_5211`/`5213` 에는 맞지 않는다.**
`IMG_5213` 은 티켓 전체가 프레임 안이고 공연일자도 인쇄돼 있다 — 다만 **엄지에 가렸다.**
그래서 `dateRaw` 가 빈 값인 것은 맞지만 원인이 다르다. 등급·가격·장소는 이 컷에서 읽힌다.

**⑥ "어느 좌석이 사용자 자리인지 모른다"는 2026-04-01 건에서는 알 수 있다.**
`IMG_9739`~`9742` 의 티켓 2장은 **예매자명이 서로 다르다**(앞 티켓과 뒤 티켓).
사용자의 다른 티켓(`IMG_1598`, `IMG_5213`, `IMG_7968`)과 같은 이름이 찍힌 쪽이
`19열 4번` 이다. (개인정보라 이름은 정답지·이 문서에 적지 않았다.)

## 4. 측정 — 저해상도 vs 원본 해상도

같은 코드(`app/services/ocrSchema.ts`), 같은 채점기(`eval/score.mjs`), **같은 날** 다시 돌렸다.
저해상도 열은 `docs/HYBRID_OCR.md` 의 옛 숫자를 옮겨 적지 않고 **오늘 재측정**했다.

| 방식 | 저해상도(기존 15장) | **원본 해상도(신규 14장)** | 할루시네이션 (저→원) |
|---|---|---|---|
| **Gemini vision** (`gemini-3-flash-preview`) | 85.0% *(문서값, 오늘 재측정 불가)* | **미측정 — 일일 쿼터 소진** | 17.8% → — |
| **하이브리드** (Vision + `gpt-5-mini-2025-08-07`) | 79.4% *(문서값)* / **78.5%** *(오늘 재측정)* | **75.3%** | 1.8% → **0.0%** |
| **Vision 단독** (배율 1,2 · 규칙 폴백) | 63.6% *(문서값)* / **62.0%** *(오늘 재측정)* | **57.7%** | 1.8% → **0.0%** |

재측정값이 문서값보다 1%p 안쪽으로 낮은 것은 그 사이 `ocrSchema.ts` 프롬프트가 바뀌었기
때문이다(리포트 상단 해시 경고 참조). **저해상도/원본해상도 두 열은 오늘 같은 코드로 잰
값끼리 비교해야 한다: 78.5% → 75.3%, 62.0% → 57.7%.**

### 4-1. Gemini vision 을 못 잰 이유

```
HTTP 429  quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier
          quotaMetric: generativelanguage.googleapis.com/generate_content_free_tier_requests
          quotaDimensions: { model: gemini-3-flash, location: global }
          quotaValue: 20
```

`RetryInfo` 는 33초라고 하지만 **분당이 아니라 일(day) 한도**다. 배치 1요청짜리
하이브리드조차 통과하지 못했다. 쿼터 회복 후 아래 한 줄이면 이 칸이 채워진다
(`eval/run.mjs` 에 `--images` / `--truth` 를 추가해 뒀다 — 기존 기본값은 그대로다):

```bash
node eval/run.mjs   --images testdata/tickets_mine --truth testdata/eval/ground_truth_mine.json --out-suffix mine
node eval/score.mjs --raw-dir eval/out/raw-mine     --truth testdata/eval/ground_truth_mine.json --out eval/out/mine-gemini
```

## 5. 결론 — 해상도가 원인이었나

**두 가지가 동시에 참이다.**

### ① 글자 오독은 해상도 때문이었다. 원본 해상도에서 **사라졌다.**

저해상도 15장에서 틀린 26개 필드는 대부분 **글자가 뭉개져 생긴 오독**이다:

```
손열음의 음.악.편.지.I  →  손열음을의 음.악·편지.I
한.러수교 30주년 기념 음악회  →  한 리수고 30주년 기념 음액회
객석1층 C구역 08열 01번  →  백석1층 C구역 08열 01번
1층 A블록 15열 10번  →  1층 A품부 15열 10번
2023-07-31  →  2021-07-31
소프라노 박혜상 리사이틀  →  소프라노 박혜상 리사이를
등급 6건 / 블록 2건 / 날짜 3건 — 아예 읽지 못해 빈 값
```

**원본 해상도 14장에서 틀린 24개 필드 중 이런 글자 오독은 0건이다.**
`date` 100%, `venue` 100%, `grade` 100%, `title` 문자유사도 0.912, 할루시네이션 0.0%.
완전 아웃포커스 3장(`5212`/`9623`/`9624`)에서는 **전 필드 기권**했다 — 지어내지 않았다.
사용자가 확인한 `"좌석: 객석 1층 P구역 06열 27번" confidence 1.00` 은 재현된다
(`IMG_1598` 은 전 필드 정답).

### ② 그런데 전체 정확도는 오르지 않았다(78.5% → 75.3%). 실패 원인이 **바뀌었다.**

원본 해상도의 오답 24개를 전부 분류하면:

| 원인 | 필드 수 | 예 |
|---|---:|---|
| **겹친 티켓 2장 중 다른 장을 읽음** | 11 | `01열 08번` 대신 동반석 `01열 09번`, `30,000원` 대신 동반권 `21,000원`, 두 장을 섞어 `1층 D블록 12열` |
| `(4.1)` 부제를 title 에 넣는가 (표기 규약) | 5 | 기대 `…국립심포니오케스트라 (4.1)` vs 출력 `…국립심포니오케스트라` (유사도 0.923) |
| 프레임 밖·손가락에 가린 글자 | 6 | 엄지에 가린 `정명훈 &`, 둘째 줄이 프레임 밖인 `합창음악Ⅱ 〈미사 글로리아〉`, 회색 밴드의 작은 `1층` 누락 |
| Vision 1단계 잡음/오독이 전파 | 2 | `LP구역` → `D구역` (§3-2 ③) · title 앞에 옆 티켓 조각 `~7` 가 붙음 |
| **글자 뭉개짐** | **0** | — |

**저해상도 스크린샷은 단일 티켓을 정면에서 스캔한 이미지라 이 문제가 아예 없다.**
실제 사용자는 티켓을 **2장씩 겹쳐 들고** 찍는다(14장 전부). 그래서 원본 해상도로 옮기면
"글자를 읽는 문제"는 풀리고 **"두 장 중 내 자리가 어느 쪽인가"** 라는 새 문제가 드러난다.

같은 정답지에서 겹친-티켓 선택(11필드)과 `(4.1)` 규약(5필드)을 눈감아 주면
하이브리드는 **91.8%**(89/97) 다. 즉 **판독 능력은 이미 90%대이고, 남은 손실은 판독이 아니라 선택이다.**

### ③ 그래서 무엇을 해야 하나

1. **"티켓이 여러 장이면 무엇을 골라야 하는가"를 프롬프트/스키마에 명시해야 한다.**
   지금 `OCR_RESPONSE_SCHEMA` 에는 좌석이 하나뿐이라 모델이 임의로 고른다.
   `seats[]` 로 전부 뽑고 UI 에서 사용자가 고르게 하는 편이 정직하다.
   (`app/services/ocrSchema.ts` 는 코드 담당 소유라 이 문서에서 제안만 한다.)
2. **저해상도 벤치마크는 폐기하지 말고 "OCR 문자 정확도" 지표로 남겨야 한다.**
   두 세트가 서로 다른 실패를 잡는다.
3. **Vision 1단계 오독은 confidence 로 걸러지지 않는다**(§3-2 ③, confidence 1.0 오독).
   2단계 LLM 에 "구역 문자는 롯데 1층 = P/LP/RP/L/R/A/B/C/D/E 중 하나" 같은
   허용집합을 주면 `D` → `LP` 정정이 가능하다(`docs/SEATMAP_geometry.md` 5-1 에 표가 있다).
