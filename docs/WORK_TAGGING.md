# 작품 스타일 태깅 설계 — "쇼팽 녹턴은 장조인데 왜 슬픈가"

작성일: 2026-08-27
관련: [TASTE_MODEL.md](TASTE_MODEL.md), [RESEARCH_data_sources.md](RESEARCH_data_sources.md)

---

## 0. 문제

`TASTE_MODEL.md` 는 취향 축으로 **편성·규모·시대·악기**를 제안했다. 이건 거친 축이다.
사용자가 제기한 반례:

> 쇼팽 녹턴 몇 번은 **장조인데도 녹턴이라서 슬픈** 게 있고, 어떤 정서인지, 자연에 대한 것인지 사랑에 관한 것인지,
> 작곡가가 **전성기에 썼는지 말년에 썼는지**, **실험적인지 전통적인지** — 이런 것도 다 알아야 하잖아

맞다. 그리고 이건 **조성만으로는 절대 안 나온다.** 장조/단조는 정서의 상관 요인일 뿐 결정 요인이 아니다.

동시에 **임베딩만으로도 안 된다.** 설명 텍스트를 임베딩하면 "비슷한 글"을 찾을 뿐이고:
- 축이 무엇인지 모른다 → 사용자에게 취향을 설명할 수 없다
- 왜 추천했는지 말할 수 없다 → 블랙박스
- SQL 필터링이 안 된다 → "단조 협주곡만" 같은 조건 불가
- 사용자가 고칠 수 없다

## 1. 해법 — 축을 사람이 정하고, LLM이 값을 매긴다

임베딩에 축 발견을 맡기지 않는다. **축을 명시적으로 정의하고** LLM에게 그 축의 값을 매기게 한다.

```ts
interface WorkStyle {
  workId: string;

  /** 정서 좌표. 조성과 독립이다 — 장조여도 valence 가 음수일 수 있다. */
  mood: {
    valence: number;   // -1 어두움 … +1 밝음
    energy: number;    //  0 정적 … 1 격렬
    tension: number;   //  0 이완 … 1 긴장
  };
  moodTags: string[];        // ['서정적','그리움','우아함'] — 사람이 읽는 라벨

  /** 주제 */
  subject: 'absolute' | 'nature' | 'love' | 'death' | 'religious'
         | 'patriotic' | 'literary' | 'dance' | 'other';

  /** 작곡가 생애에서의 위치 — LLM 아님, 계산값 (§3) */
  lifePhase: 'early' | 'middle' | 'late';
  lifeRatio: number;         // 0..1

  /** 작곡가의 도전 — 이 작품이 당대 관습에서 무엇을 깼는가.
   *  ⚠ 3단계 열거형으로는 표현이 안 된다 (2026-08-27 정정, §9).
   *  "베토벤이 당시 새로 나온 포르테피아노를 처음 본격 활용했다" 같은 건
   *  traditional/experimental 어디에도 안 들어간다. 서술이 필요하다. */
  innovations: {
    kind: 'instrument' | 'form' | 'harmony' | 'orchestration' | 'genre' | 'other';
    text: string;              // 무엇을 어떻게 새로 했는가
    evidence: string[];        // 근거 URL
    confidence: number;
  }[];

  /** 연주자의 도전 — 작품이 아니라 프로그래밍 선택. 위와 완전히 다른 것이다.
   *  LLM 에게 묻지 않는다. 연주 빈도에서 계산된다 (§9). */
  performerRarity?: number;    // 0..1, 낮을수록 자주 연주되는 곡

  /** 짜임새 */
  texture: 'melodic' | 'virtuosic' | 'contrapuntal' | 'dramatic' | 'coloristic';

  evidence: string[];        // 근거 URL
  confidence: number;        // 0..1 — 낮으면 분석에서 가중치를 낮춘다
  taggedBy: 'llm' | 'rule' | 'user';
}
```

### 왜 이 형태인가

| 요구 | 이 설계가 답하는 방식 |
|---|---|
| "장조인데 슬픈" | `key` 와 `mood.valence` 를 **분리된 축**으로 둔다. 모순이 아니라 그냥 데이터다 |
| "자연인가 사랑인가" | `subject` 열거형 |
| "전성기인가 말년인가" | `lifePhase` — 계산값이라 정확하다 (§3) |
| "실험적인가 전통적인가" | `innovation` |
| 해석 가능성 | 축에 이름이 있어 사용자에게 문장으로 말할 수 있다 |
| 수정 가능성 | `taggedBy: 'user'` 로 덮어쓸 수 있다 |

## 2. 축이 실제로 곡을 가르는가 — 검증 예시

같은 작곡가·같은 악기·같은 시대인데 갈려야 한다.

| | 녹턴 Op.27-2 | 연습곡 Op.10-4 | 장송행진곡 소나타 Op.35 |
|---|---|---|---|
| 작곡가 | 쇼팽 | 쇼팽 | 쇼팽 |
| 편성 | 독주(피아노) | 독주(피아노) | 독주(피아노) |
| 시대 | 낭만 | 낭만 | 낭만 |
| 조성 | **내림라장조** | 다단조 | 내림나단조 |
| **valence** | **−0.3** | −0.1 | **−0.8** |
| **energy** | **0.2** | **0.9** | 0.6 |
| **texture** | **melodic** | **virtuosic** | **dramatic** |
| **subject** | absolute | absolute | **death** |
| **lifePhase** | middle | early | middle |

기존 축(작곡가·편성·시대·악기)으로는 **셋이 완전히 동일**하다. 새 축에서는 확연히 갈린다.
그리고 첫 곡이 **장조인데 valence 가 음수**다 — 사용자가 지적한 바로 그 경우다.

## 3. `lifePhase` 는 LLM 을 쓰지 마라 — 계산된다

```
lifeRatio = (작곡연도 − 출생연도) / (사망연도 − 출생연도)

쇼팽 1810–1849 (39년), Op.27 은 1835년
→ (1835 − 1810) / 39 = 0.64 → middle
```

- 작곡연도는 Open Opus / Wikidata 에 있다. 없으면 **작품번호로 보간** (같은 작곡가의 알려진 Op.↔연도 쌍으로 단조 회귀)
- 경계: `< 0.33 early` / `< 0.70 middle` / `>= 0.70 late` (작곡가마다 다를 수 있어 조정 가능)
- **요절한 작곡가 주의**: 모차르트(35세)·슈베르트(31세)의 "말년"은 30대 초반이다. 절대 나이가 아니라 **비율**로 재야 하는 이유다
- 미완성·사후출판 작품은 작품번호와 작곡연도가 어긋난다 → 작곡연도 우선, 없으면 `confidence` 하향

**LLM 에게 물으면 느리고 비싸고 매번 다른 답이 나온다.** 산수로 되는 걸 추론에 맡기지 않는다.

## 4. 데이터 출처

| 축 | 출처 | 비용 | 방법 |
|---|---|---|---|
| 장르·조성·번호·작품번호 | **곡 제목 파싱** | 0 | 정규식 |
| 작곡가·epoch | **Open Opus** (CC0, 24,975곡) | 0 | 덤프 1개 |
| 한글 작곡가명 | **Wikidata SPARQL** (207/220) | 0 | 조사 완료 |
| 생몰년·작곡연도 | **Wikidata** | 0 | SPARQL |
| 악장·템포 지시어 | **예당 상세페이지** | 0 | 확보 경로 있음 |
| 편성 정확도 | **IMSLP** (`Category:For piano`) | 0 | Crawl-delay 2초 |
| **mood / subject / innovation / texture** | **LLM 1회 태깅 + 검색 근거** | 유료·1회성 | ← 여기만 돈이 든다 |

### 규모

24,975곡 전부 할 필요 없다. **한국 클래식 공연에 실제로 나오는 곡**은 훨씬 적다.

```
상위 1,000 ~ 2,000곡
  × 배치 50곡/요청
  = 20 ~ 40 요청
  → 하루면 끝. 한 번만 하고 영구 재사용
```

우선순위: ① 사용자 관람 이력에 실제 등장한 곡 → ② 예당·롯데 최근 프로그램 빈출곡 → ③ 표준 레퍼토리

## 5. 임베딩은 어디에 쓰는가

**주축은 태그, 보조가 임베딩.** 순서가 반대면 해석 불가능한 블랙박스가 된다.

임베딩이 필요한 지점은 셋뿐이다:

1. **곡목 문자열 매칭** — `"쇼팽 전주곡 24개"` ↔ `"Chopin: 24 Preludes Op.28"`
   (단, 조사 결과 **2단계 매칭(작곡가 먼저 → 작품)이 임베딩보다 낫다**. `Op.28`↔`Op.23` 구분을 임베딩이 가장 못 한다)
2. **태그가 없는 곡** — 무명·신작. 설명 텍스트 임베딩으로 근사
3. **"이 곡과 비슷한 곡"** — 태그 축으로 안 잡히는 미묘한 유사성

```sql
-- 태그가 주, 임베딩이 보조
SELECT w.* FROM works w
WHERE w.forces = 'concerto'
  AND w.mood_valence < 0
  AND w.texture = 'melodic'
ORDER BY w.embedding <=> :user_taste_vector   -- pgvector, 동점 처리용
LIMIT 20;
```

## 6. 정확도 — 정직하게

| 곡 유형 | LLM 태깅 신뢰도 | 처리 |
|---|---|---|
| 표준 레퍼토리 (쇼팽 녹턴, 베토벤 교향곡) | 높음 — 학습 데이터가 두껍다 | 그대로 사용 |
| 준유명작 | 중간 | `confidence` 반영 |
| 무명·위촉초연·지역 악단 신작 | **낮음** | **`null` + 추측 금지** |

**검증 방법** (OCR 에서 쓴 방식 그대로):
- 사용자가 잘 아는 곡 **20~30개로 골든셋**을 만든다
- LLM 태깅을 그 골든셋에 대고 채점 — `mood.valence` 는 부호 일치율, 열거형은 정확도
- 프롬프트를 바꿀 때마다 회귀 측정
- **감으로 판단하지 않는다.** 하네스가 이미 있다

**알려진 한계**
- `mood` 는 본질적으로 주관적이다. 목표는 "정답"이 아니라 **일관성** — 같은 곡에 항상 비슷한 값이 나오는 것
- 연주에 따라 성격이 달라진다 (같은 곡도 지휘자마다 다르다). 우리는 **작품** 단위로만 태깅하고 연주 해석은 다루지 않는다
- 서양 클래식 중심 어휘다. 국악·현대음악엔 잘 안 맞을 수 있다

## 7. 축은 고정이 아니다 — 피드백이 골라준다

**우리가 정한 축이 완벽할 필요가 없다.** 좋아요/싫어요가 쌓이면 **어떤 축이 이 사용자에게 예측력이 있는지** 데이터가 말해준다.

```
사용자 A: texture 와 energy 가 강한 예측자, subject 는 무관
사용자 B: subject=nature 일 때만 반응, mood 는 무관
```

축별 예측력을 계산해 개인별 가중치를 둔다 (로지스틱 회귀 수준이면 충분하다 — 딥러닝 불필요).

**이게 진짜 개인화다.** 모두에게 같은 축이 중요한 게 아니라, **사람마다 다른 축이 살아난다.**

표본이 적을 때는 가중치를 균등에 가깝게 두고(축소 추정), 데이터가 쌓이며 벌어지게 한다.

| 1 | 곡 제목 파서 — 장르·조성·번호·작품번호 | **없음. 지금 가능** |

## 9. 정정 (2026-08-27) — `innovation` 축이 두 가지를 뭉갰다

사용자 지적:

> 연주자는 별로 안 유명한 곡을 치는 게 도전적이지만, 베토벤은 그 당시 처음으로 발명된 피아노라는 걸
> 사용한 게 도전적인 거고, **작곡가의 도전적인 거랑 연주자의 도전적인 거는 다르다.**
> 작곡가마다 당연히 variation 을 자기 곡에 넣으려고 하니까 **그 variation 이 뭔지를 말하라**는 게 내 의도였다.

맞다. §1 의 `innovation: 'traditional' | 'idiomatic' | 'experimental'` 은 **두 개의 다른 것을 한 축에 욱여넣었다.**

| | 주체 | 성격 | 출처 |
|---|---|---|---|
| **연주자의 도전** | 프로그래밍 선택 | 작품 **외부** 속성. 같은 곡도 시대·지역에 따라 희귀도가 다르다 | **연주 빈도** — 데이터·무료·정확 |
| **작곡가의 도전** | 작품 자체 | 작품 **내부** 속성. 고정값 | 음악사 지식 — 텍스트/LLM |

### 왜 열거형으로는 안 되는가

"베토벤이 당시 확장된 음역의 포르테피아노를 전제로 작곡했다"는 `traditional`도 `experimental`도 아니다.
**무엇을** 새로 했는지가 정보의 전부인데 3단계 라벨은 그걸 통째로 버린다.

→ `innovations` 를 **`{kind, text, evidence}` 배열**로 바꾼다. `kind` 만 열거형이고 내용은 서술이다.

### `performerRarity` 는 계산값이다

`REPERTOIRE_ANALYSIS.md` (수집 중) 의 연주 빈도에서 바로 나온다:
```
performerRarity(work) = 1 − (해당 작품 연주 횟수 / 최다 연주 작품의 횟수)
```
LLM 에게 "이 곡이 희귀한가" 물어볼 필요가 없다. **10년치 데이터가 답을 갖고 있다.**

같은 논리로, 연주자 단위 지표도 나온다:
```
performerAdventurousness(연주자) = 그가 연주한 작품들의 평균 performerRarity
```
임윤찬·손열음이 실제로 희귀 레퍼토리를 고르는지가 **숫자로** 검증된다.

## 10. 하이라이트 — 유튜브 댓글 타임스탬프 (2026-08-27 추가)

사용자 제안:

> gemini api 로 제일 댓글 많은 부분 찍어주면 안 되나? 하이라이트 초에다가
> "한국인들이 여기 들으려고 맨날 옴" 이런 식으로 댓글 달아놓던데

**이게 LLM 에게 묻는 것보다 정직하다.** 같은 원칙이다 — 데이터에서 나오게 하고, 추론에 맡기지 않는다.
LLM 에게 "클라이맥스가 몇 분이냐" 물으면 검증 불가능한 값을 그럴듯하게 지어낸다. 댓글은 **실제 사람들이 찍은 좌표**다.

### 파이프라인

```
작품 → (캐시된) YouTube 영상 ID
     → commentThreads.list
     → 정규식으로 타임스탬프 추출  /\b(\d{1,2}):(\d{2})\b/
     → 빈도 집계 → 상위 지점
     → (선택) 그 시각 언급 댓글들을 LLM 이 한 줄 요약
```

**타임스탬프 추출 자체에 LLM 은 필요 없다.** 정규식과 카운팅이다.
LLM 은 "왜 거기가 좋은지"를 요약할 때만 쓴다 — 그것도 선택이다.

### 할당량

| API | 유닛/호출 | 하루 10,000 기준 |
|---|---:|---|
| `search.list` (영상 찾기) | **100** | 100회 |
| `commentThreads.list` (댓글) | **1** | 사실상 무제한 |

**병목은 댓글이 아니라 영상 찾기다.** 곡 사전은 한 번만 만들고 영상 ID 를 영구 캐시하면 실질적 제약이 아니다.

### 한계 (정직하게)

- **댓글이 꺼진 영상**이 있다. 클래식은 대체로 켜져 있지만 전부는 아니다
- 타임스탬프 댓글은 **조회수 많은 영상에 몰린다.** 무명 연주는 댓글이 없다 → `null`
- **영상마다 시작 지점이 다르다** (인사말·박수 30초 등). 같은 곡도 영상이 다르면 타임스탬프가 안 맞는다
  → **`{videoId, seconds}` 를 반드시 묶어서 저장**한다. 초만 따로 쓰면 틀린다
- 유튜브 플레이어의 **"가장 많이 다시 본 구간"(heatmap)** 이 더 정확하지만 **공식 API 에 없다.**
  웹 플레이어에만 있어 긁으면 ToS 위반 소지가 있다. **댓글은 공식 API 라 깨끗하다**
- 댓글은 인기의 지표지 음악적 중요도의 지표가 아니다. 유명한 선율에 쏠린다

### 데이터 모델

```ts
interface WorkHighlight {
  workId: string;
  videoId: string;           // 타임스탬프는 이 영상에서만 유효하다
  seconds: number;
  mentionCount: number;      // 몇 개의 댓글이 이 지점을 언급했나
  sampleComments: string[];  // 근거로 원문 보존
  summary: string | null;    // LLM 한 줄 요약 (선택)
  source: 'youtube-comments';
}
```

### 그리고 더 강한 신호

`TASTE_MODEL.md` §4 의 앙코르와 같은 논리로, **사용자 본인이 찍은 순간**이 남의 댓글보다 강한 취향 신호다.
```ts
myMoment?: { seconds: number; note: string };   // "오늘은 3악장이 좋았다"
```
AI 가 "이 곡의 하이라이트는 여기"라고 알려주는 것보다, **그날 본인이 뭐가 좋았는지 적어둔 게** 분석에 훨씬 쓸모 있다.
