## 0. 결론 — 이전 조사의 예측은 **절반만 맞았다**

`RESEARCH_data_sources.md` §3-3 의 결론은 이랬다:

> 곡목은 KOPIS에서 안 나오므로, 롯데콘서트홀 공연의 곡목은 폴백(사용자 입력 / 소개이미지 OCR)에 의존한다.
> **예술의전당 대비 품질 격차가 구조적으로 생긴다** — 이건 제품 설계에서 인정하고 가야 한다.

| 이전 조사의 주장 | 판정 | 실측 |
|---|---|---|
| 롯데는 JSON 엔드포인트가 없다 | ❌ **틀렸다** | 월간 캘린더 JSON API가 있고, 상세페이지는 **서버렌더된 Vue `data` 객체**에 공연 메타를 통째로 담고 있다 |
| 콘텐츠 ID가 암호화된 불투명 토큰이다 | ❌ **틀렸다** | 공연 상세 URL은 `/product/ko/performance/261157` — **평범한 정수 ID**다 (암호화 토큰은 홍보 배너용 CMS 경로였다) |
| 곡목은 텍스트로 얻을 수 없다 | ⭕ **대체로 맞다** | 텍스트로 곡목이 있는 공연은 **2,163건 중 385건(17.8%)** 뿐 |
| 곡목은 OCR 폴백에 의존한다 | ⭕ **정확히 맞다** | 최종 확보 1,501건 중 **1,116건(74.4%)이 OCR로 얻은 것**이다 |
| 예당 대비 구조적 품질 격차가 생긴다 | △ **줄일 수 있었다** | 곡목 추출률 **예당 79.6% vs 롯데 69.4%** — 10%p 차이는 남지만 "구조적 격차"라 부를 정도는 아니다 |

**한 줄 요약: "곡목은 있다. 텍스트가 아니라 이미지 안에 있을 뿐이고, 무료 로컬 OCR로 대부분 꺼낼 수 있다."**

그리고 두 홀의 레퍼토리에 대해서는:

**"같은 곡을 하지만, 그 위에 롯데만의 층이 하나 더 있다."**
예당 상위 50곡 중 롯데에 한 번도 안 나온 곡은 **단 2곡**이고, **둘 다 실내악**이다(§5-2).
반대로 롯데 연주의 **35%** 는 예당 코퍼스에 아예 없는 곡이다. 그 차이의 정체는 §5-3, §5-4 에 있다.

## 1. 수집 경로 — 이전 조사가 놓친 것

### 1-1. 월간 일정: 2단계 불투명 키 경로

롯데 사이트는 월간 캘린더를 이렇게 부른다 (사이트 자신의 JS가 하는 그대로 따라 했다):

```
1) POST /api/historyBack/create      value={"Year":2016,"Month":9,"SelectDay":null,"Today":1,"VenueID":0}
   → {"Code":0,"Tag":"MGIxMmU2NTIxODQ4NDhjZDhmN2E5ZGU3MDNhZjVmMWI%3d"}   (서버가 필터를 저장하고 키를 준다)
2) GET  /product/performance/month/calendar?q=<키>
   → {"Code":0,"Tag":{"Filter":{...},"Weeks":[[{"Day":1,"Times":[{PerformanceID, Title, Place, ...}]}]]}}
```

키가 불투명해 보이지만 **암호가 아니라 서버측 세션 저장 키**다. 필터 JSON을 그대로 넣으면 그대로 나온다.
연도 선택 UI는 `2016 ~ 올해+2` 를 노출한다 — 개관연도부터 전부 조회 가능하다.

### 1-2. 상세페이지: 서버렌더된 Vue 데이터

예당은 HTML 본문을 긁어야 했지만, 롯데는 페이지 안에 이게 통째로 박혀 있다:

```js
new Vue({ el: "#body", data: {"PerformanceID":257367,"PerformanceName":"장 기유 파이프오르간 리사이틀",
  "GenreName":"오르간(공연)","ProductionTypeName":"기획","PlayDate":"2016.09.20","Place":"롯데콘서트홀",
  "Descriptions":[{"Name":"출연","Value":"연주 l 장 기유"}, ...],
  "Details":[{"Name":"공연소개","Value":"<p><img src=...></p>"}, {"Name":"아티스트","Value":"..."}], ...} })
```

**장르(`GenreName`)가 문자열로 제공된다** — 예당의 숫자 코드 추측보다 훨씬 낫다.
`오케스트라`, `실내악`, `독주`, `합창`, `오르간(공연)`, `콘서트오페라`, `고음악`, `크로스오버`, `재즈`… 40여 종.

### 1-3. robots.txt / 예절

- `robots.txt`: `www.lotteconcerthall.com`, `lotteconcerthall.com` 모두 **404 (규칙 파일 자체가 없다)**. 금지 대상 없음

- HTML 3,842건 + 이미지 2,201건 = **6,043 요청**, 총 소요 약 2시간

### 2-3. 텍스트 vs OCR — 이번 작업의 핵심 숫자

| 곡목을 얻은 경로 | 공연 수 | 비중 |
|---|---|---|
| 본문에 **텍스트**로 프로그램이 있음 (`heading`/`cluster`) | **385** | 25.6% |
| 상세**이미지 OCR**로 얻음 (`ocr-heading`/`ocr-cluster`) | **1,116** | **74.4%** |
| 합계 | **1,501** | 100% |

**OCR 없이는 추출률이 17.8% 였다. OCR 후 69.4% 다 — 3.9배.**

> ⚠️ **macOS Vision 을 쓸 때 반드시 알아야 할 것: 세로로 긴 이미지는 잘라서 넣어야 한다.**
> 롯데 상세이미지는 `700 × 8,211px` 같은 형태가 흔하다. 통째로 넣으면 Vision 이 내부적으로 축소해
> 한글이 뭉개진다 — **실측: 8,211px 이미지 통짜 = 11줄, 세로 1,200px·겹침 150px 타일 분할 = 177줄.**
> `tools/lotte_ocr.py` 가 이 타일 분할과 겹침 중복 제거를 한다. 이걸 안 하면 OCR 이 "안 되는 것처럼" 보인다.

검증 예 (쿠렌치스 & 유토피아 오케스트라, 2026-11-17, 이미지 전용 페이지):

**(a) 캘린더 API가 서버 500 을 내는 달이 3개 있다.**
`2016-11`, `2024-07`, `2025-11` 은 한국어/영어, JSON/HTML, VenueID 유무를 모두 바꿔 봐도 **일관되게 500**이다
(서버 쪽 데이터 문제로 보인다). **ID 갭 스캔으로 메웠다** — 관측된 PerformanceID 연속 구간(257352~261193)에서

**(b) 존재하지 않는 ID는 404가 아니라 메인페이지로 조용히 리다이렉트된다.**
갭 스캔 1,123개 중 **958개가 결번**이었다. HTTP 200 을 주고 `#body` Vue 블록이 없는 페이지를 돌려준다.
그래서 "HTTP 실패 0"과 "결번 958"은 모순이 아니다.

**(c) 곡목을 못 얻은 클래식 공연 662건의 내역:**

| 원인 | 건수 | 성격 |

577건의 대부분은 **애초에 곡목이 이미지 안에도 없는 공연**이다 — 포스터 + 홍보 문구만 있고 프로그램을 안 실은 대관 공연.

### 2-5. 파싱 품질

| 지표 | 값 |
|---|---|
| `parseConfidence` 중앙 / 평균 | **0.80 / 0.77** |
| — 텍스트 경로 중앙값 | 0.84 |
| — **OCR 경로 중앙값** | **0.77** (OCR 오독 여지로 -0.10 감점 반영) |
| 명시적 `PROGRAM`/`프로그램` 헤딩으로 잡음 | 1,115 (74.3%) |
| 헤딩 없이 클러스터링으로 잡음 | 386 (25.7%) |
| 작품번호(Op./BWV/K./D. 등) 추출 | 3,282 / 4,977 (65.9%) |
| 악장 목록 추출 | 561곡 |
| 인터미션 이후 위치 판별 | 707곡 |
| **앙코르** | **0건** |

**앙코르는 0건이다.** 예당(13,080건 중 1건)과 마찬가지로 사전 프로그램에 인쇄되지 않는다.
`isEncore` 필드는 남겨두되 **이 데이터로 앙코르 통계를 낼 수 없다.**

**OCR 특유의 결함 3가지 — 실측치와 함께:**

1. **세로 구분자 오독.** OCR 이 `|` 를 `I`/`l` 로 자주 읽는다. 곡 줄 분리에 치명적이라
   `lotte_parse.py` 에서 정규화한다(`(?<=\S)\s+[Il|｜ǀ丨ㅣ]\s+(?=\S)` → ` | `).
2. **산문 오염.** OCR 텍스트는 프로그램과 홍보 산문의 구조적 경계가 사라진다. 예당 파서의 방어선
   (작곡가가 줄 앞머리 + 구분자 검사)이 그대로 작동해 **오염은 연주 기록 4,431건 중 32건 = 0.7%** 에 그쳤다.
   그래도 0은 아니다 — `말러 자신도 그의 작품 중 가장 위대한 역작이라 칭한 교향곡 8번은…` 같은 줄이 섞여 있다.
3. **INTERMISSION 이 타일 경계에서 갈린다.** `INTERMISSI` + `N` 으로 쪼개져 인터미션 경계를 놓치는 경우가 있다.
   `afterIntermission` 은 참고값으로만 쓸 것.

**결론: 작품 분포의 모양은 두 홀이 사실상 같다. 다른 건 규모다.**
단, **작곡가 층은 롯데가 확실히 좁다** (상위 10명 54.8% vs 48.8%).

| 비클래식 내역 | 기타 325, 크로스오버 79, 렉쳐콘서트 46, 복합장르 43, 대중음악 22, 국악 21, 재즈 20, 뉴에이지 15, 뮤지컬 14 … |
| **대관** | **2,331건 (83.3%)** |
| **기획** (롯데문화재단 자체) | **465건 (16.6%)** |

**(a) "대중적"이라는 인상의 실체는 '크로스오버'가 아니라 '대관'이다.**
비클래식은 22.7%로 압도적이지 않다. 진짜 특징은 **공연의 83%가 대관**이라는 것이다.
롯데콘서트홀은 자체 기획보다 **남의 공연을 받는 홀**로 운영된다.
그리고 **곡목 데이터 품질이 나쁜 이유도 정확히 이것이다** — 곡목 추출 실패 662건 중 **621건(94%)이 대관**이다.

**(b) 다만 이 22.7%는 예당과 직접 비교할 수 없다.** 예당 수집은 애초에 클래식 장르 코드로 필터링해서
비클래식 공연을 수집 대상에서 뺐다. 두 홀의 "대중 공연 비율"을 비교하려면 예당을 다시 전량 수집해야 한다 — **미수집**.

## 8. 산출물 명세

### `app/data/repertoire_lotte.json` (860KB)

**`app/data/repertoire.json`(예당)과 완전히 동일한 스키마다.** 작품 `id` 도 같은 규칙으로 매겨져 있어
**그대로 병합할 수 있다** (검증: 예당 키 재현율 5,463/5,463 = 100%).

```jsonc
{
  "source": "롯데콘서트홀 공연 상세페이지 (www.lotteconcerthall.com)",
  "collectedAt": "2026-08-27",
  "range": { "from": "2016-08-25", "to": "2026-12-22" },
  "concertsParsed": 1501,
  "performances": 4431,
  "works": [
    { "id": "Rachmaninoff|op.18", "composer": "Rachmaninoff",
      "label": "라흐마니노프, 피아노 협주곡 제2번", "altLabels": ["…"],
      "form": "piano concerto", "opus": "op.18", "number": "2",
      "count": 57, "concerts": 55, "rank": 1, "rarity": 0.0, "rarityPct": 0.0004,
      "firstDate": "2016-…", "lastDate": "2026-…", "monthHist": { "12": 8, … } }
  ]
}
```

**병합 시:** 두 파일의 `works[].id` 로 조인하면 고유 작품 **6,838곡**, 연주 **17,511건**이 된다.
`count` 는 홀별로 분리 보관하는 편이 낫다 — §5-3 의 홀 성격 차이가 사라지기 때문이다.

⚠️ **병합 시 알아둘 것:** `repertoire_lotte.json` 의 id 는 예당+롯데 **합본 매핑**으로 매겨졌고,
`repertoire.json` 의 id 는 예당 단독 매핑으로 매겨졌다. 예당 작품 **38개(0.7%)** 가 두 매핑에서 다른 id 를 받는다(§5 서두).
정확한 병합이 필요하면 `tools/lotte_analyze.py` 의 `build_key_map`/`assign_keys` 로 **양쪽을 한 번에 다시 키잉**하면 된다
(`work/sac_programs/perf_events.json` 이 있으면 재수집 없이 가능하다).

## 9. 남은 일

1. **성악·합창 인덱스 확장** — 곡목 확보율이 32%로 가장 낮다. 한국 가곡·합창곡 작곡가 사전을 추가하면
   `parsed.jsonl` 의 원문에서 **재수집 없이** 되살릴 수 있다. 예당과 공유되는 작업이다.
2. **동성 작곡가 분리** (§4-3b). `Strauss` 부터. 롯데는 `Strauss`/`J.Strauss` 로 **쪼개지기도** 해서 양방향 정리가 필요하다.
3. **작품 키 표기 차이 통합** (§4-3c, §5 서두). `composer|opus` ↔ `composer|form#number` 쌍을
   합본 매핑에서 union-find 로 묶으면 겹침 비율이 38.9% → 약 40.1% 로 보정되고,
   예당 키 38개가 매핑에 따라 흔들리는 문제(재현율 99.3%)도 함께 사라진다.
4. **OCR 산문 오염 제거** (§2-5). 현재 0.7%. Vision 이 주는 바운딩박스(글자 크기·x위치)를 쓰면
   "프로그램 블록"과 "홍보 산문"을 레이아웃으로 구분할 수 있다. `lotte_ocr.py` 는 지금 box 를 버리고 있다.
5. **캘린더 500 오류 3개월** (§2-4a) — ID 갭 스캔으로 메웠지만, 사이트가 고쳐지면 정식 경로로 재확인할 것.
6. **예당 비클래식 공연 수집** — §5-5(b). "홀 성격" 비교를 완성하려면 필요하다. 현재 **미수집**.
7. **금호아트홀·롯데콘서트홀 외 공연장** — 두 홀만으로 "한국 클래식"을 대표시키면 안 된다.
