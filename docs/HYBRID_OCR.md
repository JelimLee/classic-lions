# 하이브리드 OCR — macOS Vision + LLM 구조화

> 작성 시점의 실측값만 적는다. 돌리지 않은 것은 "미측정"이라고 쓴다.

## 0. 왜 바꾸는가

Gemini vision 단독 판독은 정확했다(전체 필드 정확도 **85.0%**). 문제는 정확도가 아니라 **쿼터**다.

`gemini-3-flash` 무료 티어는 `generate_content_free_tier_requests` 가 **하루 20회**다.
**토큰이 아니라 요청 수** 제한이라, 티켓 20장을 올리면 그날 앱은 죽는다.
실제로 기준선 측정도 18장 중 4장이 429 로 실패해 14장만 채점됐다.

하이브리드는 이 제약을 구조적으로 없앤다.

```
티켓 이미지
   ↓ ① macOS Vision (무료·무제한·오프라인·1배 1.07초 / 기본값인 1+2배 2.10초 — 실측)
raw 텍스트 줄 + 줄별 confidence + 바운딩박스
   ↓ ② 여러 장을 한 요청에 묶어 LLM 구조화 (이미지 아님, 텍스트만)
구조화 JSON  (= 앱의 OCR_RESPONSE_SCHEMA 와 같은 모양)
   ↓ ③ postProcessOCR / parseSeat / normalizeDate  (앱과 완전히 같은 경로)
최종 결과
```

핵심은 **이미지를 텍스트로 바꾸면 배치가 가능해진다**는 점이다.
이미지는 장당 수백 KB라 한 요청에 여러 장을 넣기 부담스럽지만, OCR 줄은 장당 1~2KB다.
18장을 **1요청**에 넣을 수 있다. 요청 수가 장수에 비례하지 않으므로 20회/일 제한이 사실상 사라진다.

## 1. 구성 요소

| 파일 | 역할 |
|---|---|
| `tools/vision_ocr.py` | ① macOS Vision OCR. 줄별 `text` / `confidence` / **바운딩박스** |
| `app/services/hybridOcr.ts` | 체계적 오류 교정 · LLM 입력 렌더링 · 배치 프롬프트/스키마 · **응답 검증** · 규칙 폴백 |
| `tools/hybrid_ocr.mjs` | 파이프라인 CLI. Vision 캐시 · 배치 호출 · eval 하네스 형식으로 raw 저장 |
| `app/services/ocrSchema.ts` | ③ 후처리(`parseSeat`/`normalizeDate`/`postProcessOCR`). **수정하지 않는다 — import 만 한다** |

`hybridOcr.ts` 는 브라우저 API에 의존하지 않는다. Node 가 타입 스트리핑으로 그대로 import 하므로
CLI 와 앱이 **같은 코드**를 쓴다. 프롬프트를 CLI 쪽에 복사하면 그 순간 측정이 앱을 대표하지 못한다.

### ① Vision 단계

```bash
python3 tools/vision_ocr.py testdata/tickets/lotte_met_opera_2024.jpg --pretty
```

```json
{"i": 1, "text": "객석1층 B구역 15일 01번", "confidence": 1.0,
 "box": [0.073, 0.279, 0.351, 0.033], "h": 0.033}
```

- `box` 는 **좌상단 원점** 0~1 정규화 `[x, y, w, h]`. Vision 원본(좌하단 원점)을 뒤집어 낸다.
- 줄은 읽는 순서(위→아래, 왼→오른쪽)로 정렬한다. 밴드 폭은 이미지 높이의 2% 고정이다 —
  글자 높이로 나누면 큰 제목과 작은 본문이 섞인 티켓에서 같은 줄이 서로 다른 밴드로 갈라진다.
- 결과는 `work/vision_cache/<파일 sha256>[.x<배율>].json` 에 캐시한다.
  무료·로컬이라 마음껏 재실행해도 된다 (실측 18장 1+2배 37.7초 = 장당 2.10초).

### 위치 정보가 왜 필요한가

LLM 에 텍스트만 주면 "롯데콘서트홀" 이 공연장인지 주최사 로고인지, 어느 줄이 공연명인지
판단할 근거가 없다. `h`(글자 높이)와 `y`(세로 위치)를 같이 주면 "상단의 큰 글씨 = 공연명",
"우하단 스텁 = 좌석" 같은 레이아웃 규칙이 프롬프트로 표현 가능해진다.

### ② 체계적 오류 교정 (LLM 이전)

macOS Vision 은 티켓 좌석 문자열에서 **재현성 있게 같은 실수**를 한다. 언어 보정
(`usesLanguageCorrection`)이 한국어 문장 통계 쪽으로 밀어버리기 때문이다.

| 규칙 | 오류 | 교정 | 적용 조건 |
|---|---|---|---|
| R1a | `15일 01번`, `15월 01번` | `15열 01번` | 숫자 뒤 `일/월` + 그 뒤에 `N번` |
| R1b | `B구역 04일` | `B구역 04열` | 앞에 `층/구역/블록` |
| R2 | `l층`, `O1번`, `I열` | `1층`, `01번`, `1열` | 좌석 단위(`층/열/번`) 바로 앞 토큰 |

**무분별한 치환은 금지다.** `2024년 6월 20일` 의 `일/월` 을 `열` 로 바꾸면 날짜가 통째로 깨진다.
그래서 (a) 줄이 좌석 문맥(`좌석/객석/층/구역/블록/열/번` + 숫자)인지 먼저 보고,
(b) 날짜 문맥(`\d{4}년`, `N월 N일`)이면 아예 건드리지 않으며,
(c) 그 줄 안에서도 위 패턴에 맞는 부분만 바꾼다.

`--no-fix` 로 끄고 A/B 를 잴 수 있다.

### ③ LLM 배치 구조화

- 프롬프트는 **앱의 `OCR_PROMPT` 를 그대로 삽입**하고, 앞뒤로 (a) 입력이 이미지가 아니라
  OCR 줄이라는 설명과 (b) 배치·순서 규칙만 덧붙인다. 필드 정의를 다시 쓰면 앱과 갈라진다.
- 응답 스키마는 앱의 `OCR_RESPONSE_SCHEMA` 에 `index` 하나만 더한 배열이다.
- **응답 검증이 핵심이다.** `validateBatch()` 가 다음을 전부 에러로 만든다:
  - 원소 수가 입력 장수와 다름
  - `index` 중복
  - `index` 누락(구멍)

  조용히 채우면 3번 티켓의 좌석이 5번 티켓에 붙고, 평가는 그걸 "정확도 하락" 으로만 본다.
  에러가 나면 배치를 **반으로 쪼개 재시도**한다(1장까지 내려가면 그 장만 실패 처리).

### ④ 오프라인 폴백 (`--no-llm`)

LLM 없이 Vision + 정규식만으로 `RawOCRResponse` 를 만든다. 네트워크가 없거나 크레딧이
떨어져도 앱이 죽지 않아야 한다. 날짜·시각·좌석·등급·금액·공연장은 규칙으로 상당히 잡히고,
공연명은 "글자가 크고 위쪽" 으로 추정한다. **연주자와 곡목은 규칙으로 안전하게 뽑을 수
없어 빈 값으로 둔다 — 지어내지 않는다.**

## 2. 사용법

```bash
# 하이브리드 (Gemini 로 구조화)
node tools/hybrid_ocr.mjs --provider gemini --batch 20

# 하이브리드 (OpenAI 로 구조화). 키는 --openai-env 경로에서 그 자리에서 읽는다(복사 안 함)
node tools/hybrid_ocr.mjs --provider openai --model gpt-5-mini-2025-08-07

# 오프라인 폴백 — API 키 불필요, LLM 요청 0회
node tools/hybrid_ocr.mjs --no-llm

# 1단계 결과만 보기
node tools/hybrid_ocr.mjs --vision-only --only lotte_met_opera_2024.jpg

# 채점 (기준선과 같은 정답지·같은 채점기)
node eval/score.mjs --raw-dir eval/out/raw-hybrid --model <라벨> --out eval/out/<라벨>
```

### 주요 옵션

| 옵션 | 뜻 |
|---|---|
| `--provider gemini\|openai` | 2단계 프로바이더 (기본 `gemini`) |
| `--model <id>` | 기본: gemini = `ocrSchema.ts` 의 `OCR_MODEL`, openai = `gpt-5-mini-2025-08-07` |
| `--openai-env <path>` | 기본 `/Users/macbook/Desktop/ai-hedge-fund-main/.env`. **읽기만 한다** |
| `--batch N` | 한 요청에 묶을 티켓 수 (기본 20) |
| `--scales 1,2` | Vision 을 여러 배율로 돌려 줄 목록을 합친다 (기본 `1,2`) |
| `--max-requests N` | **LLM 요청 총량 상한 (기본 10)** |
| `--no-llm` | 규칙 기반 폴백 |
| `--no-fix` | 체계적 오류 교정 끄기 (A/B) |
| `--no-cache` | Vision 캐시 무시 |
| `--label <s>` | `meta.model` 라벨 override |

### 안전장치 — 요청이 폭주하지 않게

무료 쿼터(20회/일)와 유료 크레딧을 태우는 사고를 막는 장치가 셋 있다.

1. **요청 총량 상한** (`--max-requests`, 기본 10). 넘으면 남은 배치를 호출하지 않고 중단한다.
   분할 재시도는 재귀적이라, 막지 않으면 최악의 경우 `장수 × 2 × 재시도` 만큼 요청이 나간다.
2. **일일 쿼터 소진(429)은 치명적 오류로 처리**한다. 재시도도 분할도 하지 않는다 —
   쿼터가 없는데 쪼개면 요청만 더 태운다. 분당 rate limit(재시도 가치 있음)과 메시지로 구분한다.
3. 형식 오류(`BatchShapeError`)는 재호출로 낫지 않으므로 재시도 없이 곧장 분할한다.

### 키 취급

- 어떤 키도 로그·리포트·저장 파일에 남기지 않는다. API 오류 메시지는 `redact()` 를 거친다.
- OpenAI 키는 `/Users/macbook/Desktop/ai-hedge-fund-main/.env` 에서 **그 자리에서 읽는다.**
  이 저장소로 복사하지 않는다.

## 3. 평가 하네스와의 관계

하이브리드는 **기준선과 같은 정답지(`testdata/eval/ground_truth.json`)·같은 채점기(`eval/score.mjs`)**
로 잰다. `tools/hybrid_ocr.mjs` 는 `eval/out/raw-hybrid/<라벨>/<이미지>.json` 에
**하네스와 동일한 raw 레코드 형식**으로 저장하므로 채점기를 고칠 필요가 없다.

- 기존 Gemini vision 결과(`eval/out/raw/`)는 **건드리지 않는다.** 별도 디렉터리다.
- `meta.model` 은 `hybrid-<provider>-<model>` / `hybrid-vision-only` 라벨이다.
  방식이 라벨에 드러나므로 채점기가 두 방식을 하나의 숫자로 합칠 수 없다.
- `meta.hybrid` 에 배치 크기·요청 번호·적용된 체계적 교정·Vision 줄 수·Vision 지연이 남는다.

### 리포트의 "프롬프트 해시 불일치" 경고에 대해

하이브리드 raw 를 채점하면 리포트 상단에 다음 경고가 뜬다.

> 🔴 이 수치는 현재 `ocrSchema.ts` 가 아니라 이전 버전으로 만들어진 응답을 채점한 것이다.

**하이브리드에서는 정상이며 예상된 경고다.** 하이브리드의 2단계 프롬프트는 이미지가 아니라
OCR 줄을 입력으로 받으므로 `OCR_PROMPT` 와 해시가 같을 수 없다(필드 정의는 그 안에 그대로
삽입돼 있다). 응답 **스키마 해시는 일치**한다 — 같은 `OCR_RESPONSE_SCHEMA` 를 쓰기 때문이다.
경고문의 "쿼터 회복 후 재수집하면 갱신된다" 는 안내는 하이브리드에는 해당하지 않는다.

### 지연을 어떻게 셌는가

raw 의 `latencyMs` = `Vision 시간(캐시 미스일 때) + 배치 요청 지연 ÷ 배치 장수` 다.
배치 요청 지연을 그대로 장당 지연으로 쓰면 20장 배치가 "장당 72초" 로 보이는 왜곡이 생긴다.
장당 실제로 든 시간은 나눈 값이 맞다. 원 요청 지연은 `llmLatencyMs` 에 따로 남는다.

## 4. 측정 결과

### 4-0. 측정 조건 — 표본이 다르다는 점을 먼저 밝힌다

기준선(Gemini vision)은 **18장 중 4장이 429 로 실패**해 14장만 응답이 남았고,
그중 범위 내(`in`)는 **13장**이다. 하이브리드는 18장 전부 성공해 범위 내 **15장**이다.
**같은 숫자끼리 비교하려면 표본이 같아야 한다.** 그래서 두 가지를 모두 싣는다.

- **표 A**: 각 방식의 리포트 헤드라인 그대로 (표본이 다름 — 기준선 13장, 하이브리드 15장)
- **표 B**: **양쪽 모두에 응답이 있는 공통 13장**만으로 재집계 (같은 이미지·같은 채점기)

**결론을 볼 때는 표 B 를 보라.** 표 A 의 하이브리드 쪽에는 기준선이 아예 시도조차 못 한
hard 이미지 2장(`sac_saturday_concert_2023`, `sac_symphony_festival_2025`)이 더 들어 있다.

### 표 A — 각 리포트 헤드라인 (표본 다름)

| 방식 | 이미지 | 전체 정확도 | 할루시네이션 | 귀속오류 | 장당 지연 | LLM 요청 수 |
|---|---:|---:|---:|---:|---:|---:|
| Gemini vision (기준선) | 13 | **85.0%** | 17.8% (8/45) | 11.1% | 20,281 ms | 15 (+실패 4) |
| **하이브리드 (Vision + gpt-5-mini, 배치 20)** | 15 | **79.3%** | **1.8%** (1/55) | **0.0%** | 4,386 ms | **1** |
| Vision 단독 `--no-llm` (배율 1,2) | 15 | 62.0% | 1.8% (1/55) | 0.0% | 2,096 ms | **0** |
| Vision 단독 `--no-llm` (배율 1) | 15 | 58.7% | 1.8% (1/55) | 0.0% | 1,068 ms | **0** |

### 표 B — 공통 13장, 같은 채점기 (이게 진짜 비교다)

| 방식 | 전체 정확도 | date | price | seat_raw | seat.floor | seat.block | seat.row | seat.number | **seat.grade** | title | venue |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Gemini vision (기준선) | **85.0%** (91/107) | 92% | 88% | 91% | 100% | 100% | 100% | 100% | **8%** | 83% | 100% |
| **하이브리드 (gpt-5-mini)** | **79.4%** (85/107) | 77% | 75% | 64% | 100% | 80% | 89% | 89% | **58%** | 75% | 92% |
| Vision 단독 (배율 1,2) | 63.6% (68/107) | 85% | 50% | 45% | 70% | 70% | 89% | 89% | 58% | 33% | 54% |
| Vision 단독 (배율 1) | 60.7% (65/107) | 85% | 50% | 36% | 70% | 50% | 89% | 89% | 50% | 42% | 54% |

`n` 은 필드마다 다르다(정답이 있는 필드만 셈): date 13 · price 8 · seat_raw 11 · seat.floor/block 10 ·
seat.row/number 9 · seat.grade 12 · title 12 · venue 13.

### 4-1. 배치는 실제로 동작한다

**18장을 1회 요청으로 처리했다.** 재시도 0회, 분할 0회, 응답 원소 18개, index 누락·중복 0.

| | 기준선 | 하이브리드 |
|---|---:|---:|
| 이미지 18장에 필요한 LLM 요청 | 18 | **1** |
| Gemini 무료 티어(20요청/일)로 하루에 처리 가능한 티켓 | **20장** | **400장** (20요청 × 20장) |

쿼터 제약은 사실상 사라진다. 이것이 이 작업의 본래 목적이었고, **달성했다.**

### 4-2. 정확도 목표(85%)는 **달성하지 못했다**

같은 13장 기준 **79.4% vs 85.0% — 5.6%p 부족**하다.

**원인은 하나로 요약된다: macOS Vision 이 이 티켓 이미지들의 한글을 Gemini vision 만큼
정확히 읽지 못한다.** 2단계 LLM 은 1단계가 흘린 글자를 복원할 수 없다.

복원 불가능한 실측 사례:

| 티켓 | 정답 | Vision 이 읽은 것 | 결과 |
|---|---|---|---|
| `sac_opera_highlight_2023` | `2023-07-31` | `2021. 07-31` | 연도가 통째로 틀림 — 텍스트만으로는 알 방법이 없다 |
| `lotte_korea_russia_30th_2020` | `한.러수교 30주년 기념 음악회` | `한 리수고 30주년 기념 음액회` | 고유명사라 교정 대상이 아니다 |

## 5. 앱 통합 인터페이스 (이번 범위 밖 — 형태만 확정)

`app/services/hybridOcr.ts` 는 **HTTP 호출을 하지 않는다.** 호출자가 `BatchStructurer` 를
구현해 넣는다(앱은 `geminiService`, 평가는 `tools/hybrid_ocr.mjs`).

```ts
import { structureVisionPages } from './hybridOcr.ts';
import { postProcessOCR } from './ocrSchema.ts';

const { results, fixes, usedLlm } = await structureVisionPages(
  pages,          // VisionPage[] — 네이티브 브리지가 준 Vision 결과
  structurer,     // BatchStructurer | null (null 이면 규칙 폴백)
  { noLlm: offline },
);
const ocrResults = results.map(postProcessOCR);   // ← 앱과 완전히 같은 경로
```

앱에 붙일 때 남은 일:

1. **브라우저에서 Vision 을 어떻게 부를 것인가.** 현재 1단계는 `python3 tools/vision_ocr.py` 다.
   웹앱에서는 쓸 수 없다. 선택지는 (a) 로컬 헬퍼 프로세스/네이티브 래퍼, (b) 브라우저 내
   OCR(WASM Tesseract 등), (c) 서버 사이드. **(b)는 정확도가 macOS Vision 과 다르므로
   이 문서의 측정값이 그대로 옮겨가지 않는다.**
2. 배치를 **언제** 묶을 것인가. 사용자가 티켓을 한 장씩 올리면 배치 이점이 없다.
   "여러 장 한꺼번에 올리기" UI 또는 업로드 큐(N초/ N장 모이면 전송)가 필요하다.
3. 오프라인/쿼터 소진 시 `--no-llm` 경로로 자동 전환하고, 그 사실을 UI 에 표시.

## 6. 시도했다가 버린 것 (실측 근거)

같은 함정을 다시 파지 않도록 남긴다.

| 시도 | 결과 | 결론 |
|---|---|---|
| `usesLanguageCorrection = False` | 줄별 confidence 가 전반적으로 떨어지고 판독도 나아지지 않았다 (`한가수고 3주년 개념 올직해`) | **켜 두는 것이 낫다** |
| `setCustomWords_` 에 공연장·좌석 어휘 주입 | 출력이 `corr=ON` 과 **한 글자도 다르지 않았다** | 효과 없음 |
| 4배 확대 후 OCR | 1배·2배보다 오히려 나빠지는 줄이 많았다 (`2022-0733`) | 배율은 무한정 키울 게 아니다 |
| **1배 + 2배 결과 병합** | 2배에서만 살아나는 줄이 있었다: `30,000원`(1배는 `30.000명`), `1층`(1배는 `⅞층`), `일반`(1배는 `얼반!`) | **채택** (`--scales 1,2`) |

배율 병합은 무료·로컬이라 후보를 늘리는 비용이 사실상 0이다. 어느 판독이 맞는지는
2단계 LLM 이 고르게 하고, 프롬프트에 "중복은 같은 값의 다른 판독이지 서로 다른 값이 아니다"
를 명시했다.

## 7. 덤으로 고친 것 — `eval/lib/gemini.mjs` 가 `thinkingConfig` 를 버리고 있었다

`app/services/ocrSchema.ts` 는 OCR 호출 설정을 이렇게 export 한다.

```ts
export const OCR_GENERATION_CONFIG = {
  temperature: 0,
  thinkingConfig: { thinkingLevel: 'MINIMAL' },
};
```

그런데 `eval/lib/gemini.mjs` 의 `generateOcr()` 에는 이 설정을 받는 인자가 아예 없었고,
`run.mjs` 도 넘기지 않았다. 결과적으로 **평가는 thinking 기본값으로 호출**됐다.
앱은 `MINIMAL` 로 호출하는데 평가는 아니었으니, 리포트의 지연·토큰·비용은 앱을 대표하지 못했다.

**고친 내용**

- `generateOcr({ ..., generationConfig })` 인자 추가 → `generationConfig` 에 그대로 펼쳐 넣는다.
  `temperature` 명시 인자(`--temperature`)가 있으면 그것이 우선한다.
- `run.mjs` 가 `mod.OCR_GENERATION_CONFIG` 를 넘긴다. 없으면 경고를 찍는다.
- **`genConfigHash` 를 캐시 키에 추가**했다. thinking 설정이 바뀌면 지연·토큰이 달라지므로
  옛 캐시를 재사용하면 안 된다. `meta.generationConfig` 에 실제 값도 기록한다.

**⚠️ 그래서 기준선의 "평균 지연 20.3초" 는 재측정 대상이다.**
그 수치는 `thinkingLevel: MINIMAL` 없이 잰 값이다. 앱이 실제로 내는 지연은 이보다 훨씬 짧을
가능성이 높다(`ocrSchema.ts` 주석은 3초대를 기대한다). **다만 Gemini 무료 쿼터가 소진돼
이번에는 재측정하지 못했다 — 미측정이다.** 쿼터 회복 후 아래 한 줄이면 갱신된다.

```bash
node eval/run.mjs           # genConfigHash 가 바뀌었으므로 캐시가 자동 무효화되어 전부 재호출된다
node eval/score.mjs
```

## 8. 남은 블로커 / 다음에 할 일

우선순위 순.

1. **Gemini 프로바이더로는 아직 한 번도 측정하지 못했다.**
   `--provider gemini` 는 구현·검증돼 있지만, 첫 호출에서 `429 (일일 쿼터 소진)` 를 받았다.
   프로그램은 설계대로 재시도·분할 없이 즉시 멈췄다(요청 1회만 소모).
   **쿼터 회복 후 아래 한 줄이면 같은 표에 Gemini 열이 채워진다.**
   ```bash
   node tools/hybrid_ocr.mjs --provider gemini --batch 20
   node eval/score.mjs --raw-dir eval/out/raw-hybrid --model hybrid-gemini-gemini-3-flash-preview \
     --out eval/out/hybrid-gemini
   ```
   이번 측정은 전부 **OpenAI `gpt-5-mini-2025-08-07`** 로 했다.

2. **기준선의 "20.3초" 재측정** (7장). `thinkingConfig` 누락 상태로 잰 값이다.
   `node eval/run.mjs` 를 다시 돌리면 `genConfigHash` 가 바뀌었으므로 캐시가 자동 무효화된다.
   **역시 쿼터 대기 중이다.**

3. **정확도 85% 미달(79.4%)의 근본 원인은 1단계다.** 프롬프트로 더 짜낼 여지는 줄었다.
   남은 선택지:
   - (a) 이미지 품질을 올린다. 테스트 이미지가 웹 스크린샷 크롭이라 해상도가 낮다.
     **실제 카메라 촬영 티켓으로 정답지를 보강하면 수치가 달라질 가능성이 크다 — 미측정.**
   - (b) 저신뢰 티켓만 Gemini vision 으로 2차 패스를 돌린다(하이브리드 우선, 폴백으로 이미지 호출).
     `ocrSchema.ts` 의 `needsSecondPass()` 가 이미 그 판정을 한다. 쿼터를 아끼면서 정확도를
     되찾는 가장 현실적인 길로 보이지만 **측정하지 않았다.**
   - (c) 배율을 더 늘리거나(1,2,3) 영역별 재인식. 4배는 오히려 나빴다(6장).

4. **비결정성 미측정.** `--repeat` 에 해당하는 옵션이 하이브리드 CLI 에 없다.
   정확도 차이 몇 %p 를 해석하려면 flip rate 를 알아야 한다.

5. **앱 통합 미착수** (5장). 특히 브라우저에서 macOS Vision 을 어떻게 부를지가 미해결이다.

6. `artist` / `program` 은 **정답지에 정답이 있는 항목이 0건**이라 이 파이프라인에서도
   정확도가 검증되지 않았다. 기준선과 같은 한계다.
